# miniagent

> 一个**不依赖任何 Agent 框架**的手写终端编码智能体 ——
> 把上下文当作有限资源来管理。

---

## 为什么做这个

同类的"编码智能体"项目很多，绝大多数长这样：

```python
while True:
    resp = llm(messages, tools)
    if not resp.tool_calls:
        break
    for tc in resp.tool_calls:
        messages.append(run(tc))
```

**这段 20 行就能写完。** 而且它在短任务里跑得很好 —— 直到你让它连续读 15 个文件，
第 16 轮请求直接被服务商以"超出上下文"拒绝，中间没有任何征兆。

这个项目的全部价值，在于它处理的是那个"直到"之后的场景：

| 常见做法 | 本项目 |
|---|---|
| 上下文无限往里塞 | 有预算、有水位、有降级路径 |
| 工具结果原样回填 | 按内容形态截断 + 溢出落盘 + 可回读 |
| 超限了等报错 | 每轮请求前主动检测 |
| 截断破坏消息结构 | 三层自修复，保证降级后仍然合法 |
| 危险命令直接执行 | 策略层拦截 + 用户确认 |

## 快速开始

```bash
# 1. 准备环境（只需要 openai 一个直接依赖）
python -m venv .venv
.venv/Scripts/pip install -i https://pypi.tuna.tsinghua.edu.cn/simple openai

# 2. 配置模型（OpenAI 兼容接口即可）
cp .env.example .env
#    填写 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL

# 3. 交互模式
.venv/Scripts/python -m miniagent.cli --workspace .

# 4. 一次性任务
.venv/Scripts/python -m miniagent.cli -t "读一下 README 并总结" -w .

# 5. 跑验证
.venv/Scripts/python verify.py          # 6 个离线场景（不消耗模型额度）
.venv/Scripts/python verify.py --e2e    # 加上真实端到端
```

## 架构

```
miniagent/
├── cli.py              装配依赖 + REPL + 事件渲染
├── loop.py             ★ 手写 agent 循环 + 历史裁剪
├── llm.py              LLM 客户端（只收发纯数据，隔离 SDK）
├── safety.py           危险命令策略（纯函数，可单测）
├── tools/
│   ├── base.py         工具契约 + 注册表 + 错误兜底
│   ├── fs.py           read / write / edit / glob / grep
│   └── shell.py        shell 执行（超时 + 输出上限）
└── context/
    ├── budget.py       ★ 预算计算 + 水位检测 + 估算误差校准
    ├── truncate.py     ★ 按内容形态截断 + 溢出落盘
    └── repair.py       ★ 消息结构自修复
```

**三层依赖方向是单向的**，且有一条硬约束：

| 层 | 允许依赖 | 明确禁止 |
|---|---|---|
| `tools/` | 标准库 | 不 import `loop` / `context` |
| `context/` | 标准库 | **不调用 LLM** |
| `loop.py` | 上面全部 | 不自己算 token，一律走 `context/` |

> `context/` 不许调用模型，是因为上下文处理一旦嵌了 LLM，压缩就会**递归消耗上下文** ——
> 你为了省 token 去调一次模型，这次调用自己又要占 token。
> 所以 budget / truncate / repair 全是纯函数，可以脱网、脱离终端直接测试。

## 四个核心机制

### 1. 预算与水位（`context/budget.py`）

```
预算 = 模型窗口 − 最大输出 − 安全缓冲
```

- **最大输出**必须扣掉：不扣的话输入占满窗口后模型没有空间生成，
  表现为"回答被截断"，而这个现象很难归因到上下文管理上。
- **安全缓冲**吸收估算误差。估算必然有偏差，不留缓冲一次低估就超限。
- 估算**刻意偏保守**（中文按 1 token/字、其他按 ~3.5 字符/token），
  因为低估的代价是请求失败，高估的代价只是少用一点窗口。
- **用真实 usage 校准**：每次响应带回的 `prompt_tokens` 是唯一真值来源。
  没有这一步，"缓冲值取 1024"永远是个拍脑袋的数字。

### 2. 按内容形态截断 + 溢出落盘（`context/truncate.py`）

截断策略按工具类型区分 —— **没有通用最优策略，只有按内容形态选策略**：

| 工具 | 保留 | 理由 |
|---|---|---|
| `run_shell` | **尾部** | 编译错误、测试结果、统计输出都在末尾 |
| `read_file` | **头部** | 定义、导入、类声明在前面 |
| 其他 | 头尾各留 | 中间明确标出省略量 |

超限内容写入 `.miniagent/offload/`，截断处留下**路径和原始大小** ——
模型需要细节时可以自己读回来。这样截断就从"信息丢失"变成了"换一种更便宜的承载方式"。

**`read_file` 豁免落盘**：否则会形成"落盘 → 读那个文件 → 又超限 → 又落盘"的循环放大。

### 3. 消息结构自修复（`context/repair.py`）

工具调用协议要求严格配对。一旦配对被破坏（裁剪、中断、迁移都可能），
**服务商通常整批拒绝请求** —— 一次截断能让整个请求失败。

三步修复，**顺序不能乱**：

```
① 剥离畸形调用  →  ② 丢弃孤儿结果  →  ③ 回填缺失结果
```

- ① 必须在 ② 前：畸形调用会从"已声明"集合里消失，从而把它的结果变成孤儿；
  先清理调用再判断孤儿，才不会误判。
- ③ 必须在最后：它的依据是"已声明但没结果"，这个集合只有 ①② 做完才准确。
- **回填内容必须诚实**：明确写"结果不可用"，绝不伪造数据 ——
  伪造会让模型基于假信息推理，比报错危险得多。

### 4. 历史裁剪（`loop.py::_snip_history`）

超限时的**第一道降级**（无损，只影响本次请求，不动持久化历史）：

- **永远保留 system 消息**：丢了模型会失忆（不再遵守行为约束），
  而这种失效表现为"模型变笨了"，很难归因。
- **保留最近 N 条**：那是当前任务的现场。所以从**较早处**开始裁，
  而不是简单地"从最老删起"。
- **允许切断配对，交给 repair 兜底**：与其在裁剪处做复杂的配对感知，
  不如让下一轮的修复统一处理 —— 一个职责明确的兜底层，比每处都小心翼翼更可靠。

**裁剪救不回来时明确失败**：如果单条消息本身就超预算（比如粘进来一个超长文件），
裁剪没有任何用（超的不是历史）。这时在**请求之前**就报错返回，不浪费 token。

## 验证

```bash
python verify.py --e2e
```

6 个场景对应 6 种真实失败：预算算错 / 大输出撑爆 / 截断破坏结构 / 降级跑不通 /
长任务累积 / 端到端集成。

### 实测结果

| 指标 | 数值 |
|---|---|
| 验证项 | **37 项全部通过**（含真实端到端） |
| **治理效果（长任务模拟）** | 上下文水位 **131.7% → 7.4%**（下降 **94.4%**）<br>消息体积 **525,002 → 25,067** 字符 |
| 截断策略 | 单条结果 30,491 → 1,731 字符（shell 留尾）/ 1,670 字符（文件留头） |
| 历史裁剪 | 水位 780.0% → 120.5%，丢弃 55 条消息 |
| 估算精度 | 偏差 **+0.3%**，最差低估 **−0.8%** |
| 端到端 | 2 轮 / 1 次工具调用 / 峰值水位 1.6% / 2,957 tokens |

> 估算偏差只有 +0.3%，说明"中文按字、英文按字符"的粗估已经够用 ——
> **这条数据本身就是"为什么不需要引入 tokenizer"的论证**。

## 设计决策记录

| 决策 | 备选 | 为什么这么选 |
|---|---|---|
| 不用编排框架 | LangChain / LangGraph | 本项目要练的就是 loop 本身，框架会把这段藏起来 |
| 每轮都做完整治理，而不是只在超限时 | 惰性触发 | 治理动作很便宜（纯函数），但漏一次的代价是请求失败 |
| 裁剪 vs 压缩分两级 | 只有一种 | 裁剪无损可逆、压缩有损，先试代价小的 |
| 回填占位而不是删除调用 | 直接删 | 删掉会让历史自相矛盾（模型记得自己调过），占位保留了"发生过"的事实 |
| 工具只有 6 个 | 堆到 20 个 | 工具 schema 是每次请求的固定开销且不可裁剪 |
| 只依赖 openai | 引入 pydantic / rich / dotenv | 手写的项目，依赖越少越讲得清 |

## 已知局限

诚实列出 —— 这些是"知道但没做"，不是"没想到"：

1. **没有实现历史压缩（摘要）**。当前只有无损裁剪；真正的长会话需要摘要压缩，
   但压缩要调用模型，需要处理"压缩本身消耗上下文"的递归问题。
2. **安全策略是正则匹配，不完备**。能拦 `rm -rf`，拦不住
   `find . -delete` 或 `python -c "shutil.rmtree(...)"`。
   这层的作用是降低误操作概率，不是安全保证 —— 真正的保证是工作区隔离 + 备份。
3. **没有 tokenizer 精确计数**。估算偏差实测很小（+0.3%），
   但在长文档、代码混合的场景下偏差会更大，需要重新校准。
4. **没有多轮会话持久化**。每次启动是新会话，也没有长期记忆。
5. **单文件预算**：没有考虑按目录/模块分片处理超大代码库。
